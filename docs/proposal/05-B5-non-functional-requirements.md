# B5 — Non-functional requirements


## Content

Four non-functional requirements, one per category documented in the project README. Each row gives the requirement, the test conditions, the measurement method, and an objective pass/fail criterion.

| ID | Category | Requirement | Conditions | How measured |
|---|---|---|---|---|
| NFR-01 | Performance | **Requirement:** The API shall respond within **500 ms for at least 95% of ordinary non-AI API requests** under the agreed test load. [Documented — README § Quality Attributes]<br>Ordinary non-AI requests are API requests served without a call to the external AI provider (goals, tasks, courses, assignments and exams, habits, skills, dashboard). | **Conditions:**<br>Release-candidate build in the team's test environment with a fixed, version-controlled dataset (accounts, goals, tasks, courses, assignments, habits) identical for every run.<br>Every request carries a valid authenticated student session.<br>Calls to the external AI provider are excluded, because their duration depends on a third party the system does not control.<br>Test load **[Proposed — requires team approval]**: 50 concurrent virtual users issuing a fixed mix of read and write requests for a 10-minute steady-state run after a 1-minute warm-up. | **Method:** scripted load test against the seeded test environment; the script, its configuration, and the dataset seed are kept in the repository so the run can be repeated.<br>**Recorded measurement:** server-side response time per request, reported as the 95th percentile in milliseconds, with the number of measured requests and the number of failed requests.<br>**Pass/fail:** **Pass** when the 95th percentile is at or below 500 ms over the agreed test load; **Fail** otherwise. The configuration, the 95th-percentile value, and the request count are attached to the pull request. |
| NFR-02 | Security | **Requirement:** Every protected student-data endpoint shall require authentication and shall enforce authorization, and **zero unauthorized data access is permitted**: no protected record shall be returned or changed by an unauthenticated caller or by a caller who does not own the record, and administrator-only endpoints shall reject student accounts. [Documented — README § Quality Attributes and § Architecture principles]<br>Authorization is enforced on the backend; a control hidden in the user interface is not accepted as evidence. | **Conditions:**<br>Test environment seeded with three accounts: student A (owner), student B (a different student), and one administrator (README § Target Users; B4 FR-20).<br>Protected endpoints: student-owned data (goals, milestones, tasks, courses, assignments and exams, habits, skills, projects and portfolio, dashboard, notifications) and administrator-only endpoints (FR-20.1–FR-20.10).<br>Test cases **[Proposed — requires team approval]**, run once per protected resource family, with the expected status per case fixed in the case table before the run: **C1** no token → rejected, no protected data in the body; **C2** invalid or expired token → rejected; **C3** cross-student access, student A's token on a student B record → rejected, no student B data in the body; **C4** student token on an administrator-only endpoint → rejected; **C5** administrator token on an administrator-only endpoint → allowed; **C6** owner token on the owner's own record → allowed. | **Method:** API-level automated integration tests from the repository `tests/` folder for C1–C4 and C6, plus a manual HTTP-client check for the administrator cases C4 and C5.<br>**Recorded measurement:** one row per case — endpoint, credential used, expected status, actual status, and whether the response body contained another student's data.<br>**Pass/fail:** **Pass** only when every case returns its expected status and the count of unauthorized data accesses is zero; **Fail** if any case mismatches or any unauthorized access is observed. The case table and the test output are attached to the pull request. |
| NFR-03 | Reliability | **Requirement:** When an AI-provider request fails or returns output that violates the expected plan schema, the system shall **not lose, overwrite, or corrupt previously saved student data and shall not save a partial plan**: the saved goal, milestones, tasks, scheduled tasks, and study plan are unchanged after the failure, and the API returns a defined error instead of a partial save. [Documented — README § Quality Attributes and § Architecture principles ("Handle AI-provider errors, rate limits, and unavailable services"; "Validate AI output against an expected schema before saving it"); B4 FR-06.4 and FR-06.5] | **Conditions:**<br>Documented AI failure conditions to cover: provider error, rate limit, and unavailable service, plus invalid AI output that violates the expected plan structure.<br>How each condition is injected in the test is an implementation detail **[Proposed — requires team approval]**: provider error as an HTTP 500 response, rate limit as an HTTP 429 response with a Retry-After header, unavailable service as a failed connection, and a schema-invalid payload.<br>Both AI write paths are exercised while the provider fails: goal-plan generation (FR-05.2) and study-plan regeneration (FR-06.3).<br>The student already owns a saved goal with milestones and tasks, a saved study plan (FR-06.1), and scheduled tasks (FR-07.1); a snapshot of those records is taken before the failing request. | **Method:** API-level automated integration tests with the external AI provider replaced by a controllable test double; one test per combination of failure condition and AI write path (four conditions × two paths) **[Proposed — requires team approval]**. Each test captures the API response and before-and-after snapshots (row counts and record content) of the student's saved data.<br>**Recorded measurement:** per test — HTTP status and error code returned, row counts and record content before and after, the number of records written during the failed request, and whether the next read returns the previously saved study plan.<br>**Pass/fail:** **Pass** only when, in every test, the previously saved records are identical before and after, no record is written during the failed request, the response is a defined error rather than a successful partial save, and the previously saved study plan is still returned by the next read (FR-06.5); **Fail** otherwise. The test log and the before-and-after comparison are attached to the pull request. |
| NFR-04 | Usability | **Requirement:** In a usability test, **at least 4 of 5 first-time students** shall create a goal in natural language and review the AI-generated plan — its milestones, tasks, and deadlines visible on screen — within **5 minutes** of the start of the task, with **no more than 1 moderator intervention**. [Documented — README § Quality Attributes: a first-time test user creates a goal and reviews a generated plan within a specified time]<br>Participant count, time limit, pass threshold, and intervention limit: **[Proposed — requires team approval]**. | **Conditions:**<br>Moderated usability test of the running student web frontend, using the goal-planning task of the core system flow — enter a goal in natural language, receive the AI roadmap, review the proposed milestones, tasks, and deadlines (README § Core System Flow; B4 FR-05.1 to FR-05.3).<br>Participants: 5 students who have not used Aspirra before, given no training beyond the task statement.<br>The AI response is stubbed or recorded, so the measurement reflects the interface rather than the third-party provider's latency.<br>Timing starts when the participant first sees the goal-entry screen and ends when the participant confirms the generated milestones, tasks, and dates are visible; an intervention is any moderator guidance beyond restating the task. | **Method:** one moderated session per participant with a scripted task, screen and audio recording, and a moderator-held timer.<br>**Recorded measurement:** per participant — elapsed time in minutes, whether the task was completed, and the number of interventions.<br>**Pass/fail:** **Pass** when at least 4 of the 5 participants complete the task within 5 minutes with no more than 1 intervention; **Fail** otherwise. The task script, the per-participant results, and the recordings are stored with the test report; a failing round is re-run after the agreed usability fix and both rounds are reported. |
